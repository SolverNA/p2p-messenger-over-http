# P2P Messenger over HTTP · терминальный мессенджер

[Интерактивная схема работы](docs/architecture.html) · [Подробная логика с диаграммами](docs/architecture.md) · [Общая схема SVG](docs/architecture-overview.svg)

Один бинарник на Go с интерфейсом в терминале: беседы, сообщения, ввод, мышь, статусы доставки и соединений. Весь код приложения — в `main.go`. Веб-интерфейс заменён терминальным; сетевой WS/WSS-транспорт сохранён.

[Запуск одной командой и релизы](docs/releases.md) · [Приватность и видимые сетевые данные](PRIVACY.md)

Рабочая веб-версия сохранена в коммите `9e6c782` ветки `master`. Разработка терминального интерфейса — в `terminal-ui`. Сетевой протокол, ключи Ed25519 и формат истории совместимы с предыдущей версией.

## Запуск

Собранный `messenger-tui` работает на Linux x86_64 без Go. Для самостоятельной сборки нужен Go 1.27.1 или новее:

```sh
CGO_ENABLED=0 go build -trimpath -ldflags='-s -w' -o messenger-tui .
```

Первое подключение к своей сети:

```sh
./messenger-tui --bootstrap /ip4/PUBLIC_IP/tcp/80/ws/p2p/PUBLIC_PEER_ID
```

Настройки автоматически сохраняются после успешного запуска. В следующие разы:

```sh
./messenger-tui
```

По умолчанию данные находятся в `$XDG_DATA_HOME/p2pmessenger` либо `~/.local/share/p2pmessenger`. WS слушает 8081, прямые TCP/QUIC — 4002. Root для такого запуска не требуется. Терминал должен поддерживать UTF-8; рекомендуемый размер — от 80×24.

При отсутствии bootstrap узел ожидает входящих подключений. Никаких публичных серверов сторонних владельцев в бинарник не зашито.

## Переход с предыдущей версии

Остановите старый клиент через Ctrl+C, чтобы освободить его порты и каталог. Для своего существующего ключа и истории укажите прежний каталог. Например, для профиля `alice` из этого проекта первый запуск:

```sh
./messenger-tui --data ./alice --bootstrap /ip4/PUBLIC_IP/tcp/80/ws/p2p/PUBLIC_PEER_ID
```

Следующие запуски этого профиля:

```sh
./messenger-tui --data ./alice
```

У друга предыдущая команда использовала `~/.local/share/p2pmessenger`: этот каталог совпадает с новым значением по умолчанию при незаданном `XDG_DATA_HOME`. При другом каталоге обязательно используйте `--data`: приложение не ищет и не переносит ключи автоматически. Два процесса с одним каталогом одновременно не запускаются.

Старые бинарники `messenger` и `messenger-linux-amd64` оставлены на месте. Существующая служба на сервере не обновляется автоматически. Переписка между старой и новой версиями использует прежние протоколы libp2p.

## Управление

| Действие | Клавиша |
|---|---|
| Открыть беседу | Вставить Peer ID в «Кому», Enter; либо выбрать беседу |
| Отправить | Enter в поле сообщения, Ctrl+S либо кнопка мышью |
| Новая строка | Alt+Enter |
| Переключить поле | Tab / Shift+Tab |
| Статус сети, полный Peer ID, адреса и причины ошибок | F2 |
| Закрыть информацию | Esc / F2 |
| Скопировать свой Peer ID | F3, если терминал поддерживает OSC 52 |
| Закрыть приложение | Ctrl+Q / Ctrl+C |

Вставка многострочного текста поддерживается через bracketed paste. При включённой мыши для обычного выделения текста терминала может потребоваться Shift. В главном процессе логи пишутся в `node.log`, чтобы не портить экран.

## Если собеседник недоступен

В заголовке беседы показаны поиск, подключение, отправка и состояние канала. Если каталог не находит маршрут, отображается «не в сети / недоступен». Если адрес найден, но соединение не установлено — «не удалось подключиться». Разрыв при отправке и отказ получателя, например из-за полной истории, показываются отдельно. По F2 доступна техническая причина.

Сообщение сохраняется в очереди до подтверждения получателя. Интервал повторов для каждого собеседника увеличивается: 5, 10, 20, 40, затем максимум 60 секунд после неудачи; очередь проверяется раз в секунду. Время до следующей попытки видно в интерфейсе. Повторы сохраняют тот же ID сообщения и не создают дубликаты. Порядок сообщений одному получателю сохраняется; попытки разным получателям выполняются параллельно, до четырёх одновременно.

После восстановления связи очередь доставляется автоматически, ошибка и счётчик повторов сбрасываются. После перезапуска исходящие также остаются в очереди; первая попытка выполняется заново. Ошибочный адрес сбрасывается из локального кэша, чтобы повторный поиск получил свежую регистрацию.

«Недоступен» не доказывает, что процесс выключен: причиной может быть отсутствие маршрута, отказ публичных узлов или firewall. Отсутствие активного соединения само по себе также не помечается как доказанный офлайн. `Доставлено` означает сохранение на узле получателя, а не прочтение человеком.

## Сервер и подключение к работающему узлу

Для сервиса:

```sh
./messenger-tui --headless --data /var/lib/p2pmessenger --port 80 --reachability public
```

Низкий порт требует прав привязки — например, `AmbientCapabilities=CAP_NET_BIND_SERVICE` в systemd. Режим `public` применяется к первому заведомо доступному серверу; остальные узлы обычно используют `auto`. Без независимых проверяющих узлов AutoNAT может сохранять статус Unknown.

Чтобы открыть терминальный интерфейс уже запущенного узла из другого терминала:

```sh
./messenger-tui --data /var/lib/p2pmessenger --attach
```

Команда должна выполняться от владельца каталога или root. Для ранее созданной службы пользователь — `p2pmessenger`:

```sh
sudo -u p2pmessenger /usr/local/bin/p2pmessenger --data /var/lib/p2pmessenger --attach
```

Это относится к серверу после установки новой версии бинарника. Старая веб-версия `--attach` не поддерживает. Выход из подключённого интерфейса не останавливает службу; выход из основного интерфейса останавливает его узел.

Без полноэкранного интерфейса также можно получить JSON-состояние или поставить сообщение в очередь работающего узла:

```sh
./messenger-tui --status
./messenger-tui --send PEER_ID --message 'Привет!'
```

Управление идёт через `control.sock` внутри каталога данных. Права каталога 0700, сокета и создаваемых файлов 0600. Сетевого API управления и HTTP-интерфейса больше нет. Если stdin/stdout не являются терминалом, процесс автоматически работает без интерфейса. Старый параметр `--ui` принимается для совместимости со службой, но не открывает HTTP-порт.

## Сеть, шифрование и TLS

- Постоянный Ed25519-ключ определяет Peer ID. Каждое сообщение подписывается с отправителем, получателем, ID, временем и текстом.
- WS работает через HTTP Upgrade, WSS — HTTPS Upgrade. Обычный HTTP на сетевом порту возвращает только служебную строку.
- WS/TCP защищены Noise между конечными пирами, в том числе через Circuit Relay v2. Обычный HTTP/WS без внешнего TLS не означает открытый текст сообщений. QUIC имеет собственную защиту на основе TLS.
- WSS включается явно через `--tls-cert` и `--tls-key`. Наличие домена не включает его автоматически. Сертификат проверяется на имя подключения или IP SAN, в зависимости от адреса. Валидация не отключается.
- Для WSS по имени нужен доверенный сертификат на это имя; для WSS по IP — доверенный сертификат с соответствующим IP SAN. TLS не ограничен доменами. Сертификаты загружаются при запуске; ACME и автоматическое продление пока не реализованы.
- Дополнительно включены TCP/QUIC на порту 4002 для прямой связи и DCUtR. Это не режим исключительно HTTP. `--direct-port 0` оставляет WS/WSS; при таком ограничении следует рассчитывать на реле, а не гарантировать пробивание NAT.
- AutoRelay получает и продлевает резервации через bootstrap-узлы. Публичные узлы включают релейный сервис после определения публичной доступности.
- Подписанная запись адресов имеет монотонную версию и срок действия 3 минуты, обновляется каждые 30 секунд и при событиях libp2p. Небольшой `sequence.json` сохраняет версию отдельно от истории, уменьшая запись на диск.
- Поиск использует подключённые и bootstrap-узлы, с одним дополнительным переходом между каталогами. Это небольшой распределённый каталог, а не глобальная DHT.
- Libp2p ping отправляется подключённым пирам каждые 20 секунд. При неудаче прямого соединения используется реле, которое имеет стандартные лимиты libp2p и также может быть недоступно.

Пример WSS-сервера:

```sh
./messenger-tui --headless --port 443 --reachability public \
  --tls-cert /path/to/fullchain.pem --tls-key /path/to/privkey.pem \
  --announce /dns4/node.example.org/tcp/443/tls/ws
```

Адрес bootstrap для него: `/dns4/node.example.org/tcp/443/tls/ws/p2p/PEER_ID`. В firewall нужны соответствующий TCP-порт WS/WSS и, при использовании прямых транспортов, TCP/UDP 4002.

Один домен можно использовать для начального обнаружения публичных узлов. DNS-ротация, публикация новых узлов и выдача сертификатов в этой версии не реализованы. HTML-редирект не выпускает сертификат: при HTTPS TLS устанавливается до HTTP-запроса. Для масштабирования потребуется возвращать ограниченный набор начальных узлов, а остальную сеть обнаруживать через её протокол; каждый узел сохраняет отдельный Peer ID.

## Ограничения

История и очередь не зашифрованы на диске. Берегите `identity.key`: он позволяет выдавать себя за владельца узла. Здесь нет отдельного Double Ratchet/Signal и почтового ящика на реле: если получатель выключен, сообщение хранится у отправителя, которому тоже нужно работать для доставки.

Ограничения: 16 000 байт текста, 1 000 исходящих в очереди, 10 000 сообщений истории и 10 000 записей каталога. При заполнении истории новые сообщения не подтверждаются; автоматического удаления нет, чтобы не забыть ID принятых сообщений. До 16 bootstrap-узлов; для устойчивости используйте несколько публичных узлов и соединяйте их друг с другом.

Слушатели по умолчанию используют IPv4 и IPv6 (`--ip-family auto`). `--ip-family 4` или `--ip-family 6` оставляет входящие слушатели только выбранного семейства; настройка сохраняется. Этот параметр задаёт слушатели, а не фильтр исходящих адресов. Для проверки именно IPv6 укажите bootstrap через `/ip6/…` или `/dns6/…` и проверьте фактический адрес соединения по F2. Для доступности в интернете также нужны глобальный IPv6, маршрут и разрешение в firewall; loopback-тесты этого не подтверждают. Нет управления спамом и контактными разрешениями, криптографического аудита и гарантии прохождения любого NAT. Прямую связь между разными провайдерами необходимо проверять отдельно.

## Проверка

```sh
go test -race ./...
go vet ./...
go build -o messenger-tui .
node tests/smoke.mjs
```

Go-тесты проверяют подписи, адреса, настоящую релейную доставку, дедупликацию, поиск между каталогами, сохранение очереди, параметры конфигурации, интерфейс на эмуляторе терминала, недоступного получателя, восстановление связи и отказ получателя.

Smoke-сценарий требует Node.js и OpenSSL только для проверки. Он запускает WSS-узел и двух клиентов, проверяет локальный сокет, команды CLI, сохранение конфигурации/ключей/очереди и восстановление после смены адреса. Пробивание реальных NAT этим локальным сценарием не проверяется.

Документация: [Noise и TLS в libp2p](https://libp2p.io/docs/secure-channels-overview/), [DCUtR](https://libp2p.io/docs/dcutr/), [IP-сертификаты Let's Encrypt](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability).

Для дополнительной проверки совместимости с сохранённым старым бинарником `messenger`: `P2P_LEGACY_HUB=1 node tests/smoke.mjs`.

Проверка через IPv6: `go test -race -run TestIPv6 -v ./...` проверяет доставку по WS, TCP, QUIC и через настоящее реле на `::1`. Сценарий `P2P_IP6=1 node tests/smoke.mjs` запускает бинарники с IPv6-слушателями, проверяет WSS и отсутствие перехода соединения на IPv4.

## Windows x64

Сборка: `CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -trimpath -ldflags='-s -w' -o messenger-windows-amd64.exe .`.

В PowerShell, из папки с файлом: `.\messenger-windows-amd64.exe --bootstrap /ip4/PUBLIC_IP/tcp/80/ws/p2p/PUBLIC_PEER_ID`. После первого запуска настройки сохраняются, и достаточно `.\messenger-windows-amd64.exe`. По умолчанию данные находятся в `.local\share\p2pmessenger` внутри домашнего каталога пользователя. Для локального управления используется поддержка Unix-сокетов в современных Windows; поддержка старых версий Windows не проверялась. Синхронизация файла перед заменой сохраняется, а неподдерживаемая синхронизация каталога пропускается на Windows.
