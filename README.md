# Связь / P2P

Прототип личного мессенджера на Go и libp2p. Весь код приложения и HTML-интерфейс находятся в **main.go**. После сборки нужен один бинарник `messenger`; HTML, Node.js и Go на машине запуска не нужны. `go.mod`/`go.sum` фиксируют зависимости для сборки; `main_test.go` и `tests/` нужны для проверки.

## Быстрый запуск

Для сборки используйте Go 1.27.1 или новее (зависимости требуют не ниже Go 1.26).

```sh
go build -o messenger .
./messenger --port 8081
```

Откройте **http://127.0.0.1:8080**. На первом запуске создаются ключ и хранилище `node-data/`. Скопируйте Peer ID собеседнику; введите его Peer ID, чтобы написать сообщение. Без bootstrap-адреса узел ожидает входящих подключений, сам неизвестную сеть не найдёт.

Для постоянного запуска используйте обычный менеджер служб ОС. Приложение работает до SIGINT/SIGTERM; закрытие страницы его не останавливает.

## Своя сеть: публичный узел и клиенты

Первый узел запустите на сервере с известной внешней доступностью. Для начального узла `--reachability public` явно включает роль публичного узла: в пустой сети некому подтвердить её через AutoNAT. При наличии других узлов обычный режим — `auto`.

Без сертификата порт по умолчанию **80**, с сертификатом — **443**. Если ОС запрещает непривилегированному процессу занимать эти порты, выдайте бинарнику право привязки к низким портам или используйте другой порт. Сам мессенджер не требует root.

Пример публичного узла с сертификатом для `node.example.org`:

```sh
./messenger --data ./public-node \
  --tls-cert /path/to/fullchain.pem \
  --tls-key /path/to/privkey.pem \
  --reachability public \
  --announce /dns4/node.example.org/tcp/443/tls/ws
```

Откройте в firewall TCP 443 и, для прямых TCP/QUIC-соединений, TCP/UDP 4002. Укажите действительный DNS и сертификат. Проверка сертификатов включена; произвольный самоподписанный сертификат клиент не примет без настройки доверенного CA. После обновления сертификата перезапустите процесс.

Из журнала возьмите Peer ID публичного узла. На домашнем компьютере:

```sh
./messenger --data ./alice --port 8081 \
  --bootstrap /dns4/node.example.org/tcp/443/tls/ws/p2p/PEER_ID_СЕРВЕРА
```

Для устойчивости перечислите два-три публичных узла через запятую в `--bootstrap`. Публичные узлы также соединяйте друг с другом через `--bootstrap`, чтобы поиск проходил между их каталогами. Адрес должен содержать настоящий Peer ID, а не строку-заглушку.

За NAT клиент сам подключается к публичным узлам. Пробрасывать ему входящие 80/443 не требуется. На другом компьютере запустите такой же клиент с отдельным хранилищем. Обменяйтесь Peer ID через доверенный канал.

Локальный интерфейс на `127.0.0.1:8080` управляет **своим** узлом. На публичном сетевом порту доступна только служебная HTTP-страница и libp2p WebSocket, без доступа к истории или отправке сообщений. Для интерфейса удалённого сервера можно использовать SSH-туннель:

```sh
ssh -L 8080:127.0.0.1:8080 user@node.example.org
```

## HTTP и пробивание NAT

Узлы принимают libp2p через WS (HTTP Upgrade) или WSS (HTTPS Upgrade). Обычный HTTP и WebSocket делят один сетевой порт.

По умолчанию дополнительно включены TCP и QUIC на порту 4002: эти транспорты используются для прямой связи и DCUtR. **Это не режим исключительно HTTP.** Если разрешён только WS/WSS, отключите их:

```sh
./messenger --port 8081 --direct-port 0 --bootstrap /dns4/node.example.org/tcp/443/tls/ws/p2p/PEER_ID_СЕРВЕРА
```

В этом режиме нельзя рассчитывать на успешное пробивание NAT средствами TCP/QUIC; доступность обеспечивает реле. Один лишь номер порта 443 не превращает QUIC libp2p в HTTPS.

## Как работает связь

- При первом запуске генерируется постоянный ключ Ed25519. Peer ID содержит соответствующий публичный ключ; для поиска используется Peer ID. Приватный ключ остаётся в процессе Go и не передаётся браузеру.
- AutoNAT определяет внешнюю доступность. Публичный узел автоматически включает сервис Circuit Relay v2; скрытый получает и продлевает релейные резервации через bootstrap-узлы. Пока данных недостаточно, статус остаётся `Unknown`, а не выдаётся предположение о доступности.
- Узел публикует подписанную запись адресов с номером версии и сроком действия 3 минуты. Публикация повторяется каждые 30 секунд и при событиях изменения адресов/соединений. Изменение сети обнаруживается асинхронно; мгновенное восстановление не гарантируется.
- Подпись связывает адреса с ключом владельца; достижимость отдельно определяют механизмы libp2p. Запись с меньшей версией не заменяет более новую в действующем каталоге. Просроченные записи не используются.
- Поиск идёт через подключённые узлы и bootstrap-узлы, с одним дополнительным переходом между каталогами. Это небольшой распределённый каталог, **не глобальная DHT**; все публичные узлы не синхронизируют полную топологию.
- Для нового собеседника сначала пробуется прямое соединение, затем допускается реле. DCUtR координирует пробивание NAT через релейное соединение. При успехе libp2p может открыть прямой канал; при неуспехе сообщения остаются на реле.
- Каждые 20 секунд отправляется libp2p ping подключённым пирам, включая публичные узлы и активных собеседников. Уже установленный канал позволяет отправлять сразу, без нового поиска на каждое сообщение.
- После разрыва соединения повторяются подключение и поиск. При ошибке доставки кэш записи собеседника сбрасывается, чтобы получить новый адрес. Работоспособность после смены сети зависит от доступных публичных узлов и ограничений NAT/firewall.
- Исходящее сообщение сохраняется до попытки отправки. Получатель проверяет подпись, сохраняет сообщение и только затем подтверждает доставку. При потере ACK повтор не создаёт дубликат. Очередь повторяется примерно каждые 5 секунд после завершения предыдущих попыток; попытки имеют таймауты.

## Шифрование и хранение

Для WS/TCP используется аутентифицированный **Noise** с обменом временными ключами, для QUIC — защищённый транспорт QUIC/TLS. Ключ соединения проверяется относительно Peer ID. При Circuit Relay защищённое соединение устанавливается между конечными пирами: реле передаёт шифротекст. Дополнительно каждое сообщение подписывается постоянным Ed25519-ключом; подписываются отправитель, получатель, ID, текст и время.

Это защита канала между узлами, включая реле. Здесь нет отдельного Double Ratchet, протокола Signal или доставки офлайн-сообщений в почтовый ящик на реле. Если получатель выключен, очередь хранится у отправителя; для доставки отправитель должен снова работать. `delivered` означает сохранение на узле получателя, а не прочтение человеком.

Локальная история и очередь хранятся **без шифрования на диске**. Каталог имеет права 0700, создаваемые файлы — 0600. Берегите `identity.key`: потеря меняет вашу идентичность, копирование передаёт другому владельцу возможность выдавать себя за вас. Одновременный запуск двух процессов с одним каталогом блокируется.

Пределы прототипа: 16 000 байт текста сообщения, 1 000 ожидающих исходящих и 10 000 сообщений истории. При заполнении истории новые сообщения не подтверждаются; автоматического удаления нет, чтобы не потерять защиту от дубликатов. Каталог ограничен 10 000 записями, обработчики и размеры запросов ограничены. Релейный сервис использует стандартные квоты libp2p; исчерпанное/прерванное реле требует повторного подключения. Это прототип для небольшой сети, без управления контактными разрешениями, блокировок спама и криптографического аудита.

## Параметры

```text
--data ./node-data          Каталог ключа, истории, очереди и блокировки процесса
--ui 127.0.0.1:8080         Локальный интерфейс, разрешён только loopback IP
--port 80                  WS-порт, либо 443 по умолчанию при наличии TLS
--tls-cert PATH            PEM-сертификат с цепочкой
--tls-key PATH             Приватный ключ TLS-сертификата
--bootstrap ADDR,ADDR      До 16 адресов публичных узлов с /p2p/PeerID
--announce ADDR,ADDR       Дополнительные внешние адреса без /p2p/PeerID
--direct-port 4002         TCP и UDP/QUIC; 0 отключает эти транспорты
--reachability auto        auto | public | private
```

Сетевые слушатели этой версии — IPv4; интерфейс управления может использовать IPv4/IPv6 loopback. `--announce` добавляет известный внешний адрес, но не создаёт DNS, сертификат или правило NAT.

## Проверка

```sh
go test ./...
go test -race ./...
go vet ./...
go build -o messenger .
node tests/smoke.mjs
```

Go-тесты проверяют подделку/просрочку записей, сохранение идентичности, подписи сообщений, прямую доставку, настоящую доставку Circuit Relay с единственным релейным адресом, дедупликацию, поиск через два каталога и сохранённую очередь.

Сценарий smoke требует Node.js и OpenSSL только для теста. Он запускает три бинарника, создаёт временный доверенный TLS-сертификат, подключает клиентов к WSS-узлу, проверяет HTTP API и синтаксис JS интерфейса, перезапускает отправителя и получателя на новых портах и проверяет сохранность очереди/ключей и доставку. Временные процессы и данные удаляются.

**Пробивание NAT между разными интернет-провайдерами этими локальными тестами не проверяется.** Для такой проверки нужны два реальных NAT и публичный сервер. Успех зависит от их поведения; реле остаётся обязательным резервом.

Механизмы libp2p: [NAT traversal](https://docs.libp2p.io/concepts/hole-punching), [DCUtR](https://libp2p.io/docs/dcutr/), [WS/HTTP на одном порту](https://pkg.go.dev/github.com/libp2p/go-libp2p/p2p/transport/websocket).
