# Добавить публичный пир

Создайте Fork, добавьте адрес своего постоянно работающего узла в [public-peers.txt](public-peers.txt) и откройте Pull Request в `main`. После принятия PR клиенты получат новый список без обновления бинарника. Удаление или смена адреса делается таким же PR.

Формат — один полный libp2p multiaddress на строку:

```text
/dns4/node.example.org/tcp/443/tls/ws/p2p/PUBLIC_PEER_ID
/ip4/PUBLIC_IP/tcp/80/ws/p2p/PUBLIC_PEER_ID
/ip6/PUBLIC_IPV6/tcp/80/ws/p2p/PUBLIC_PEER_ID
```

Замените заглушки реальными значениями. Для IPv4 и IPv6 одного узла используйте один Peer ID и отдельные строки. Допустимы WS и WSS с ненулевым TCP-портом. Для WSS нужен доверенный сертификат. `/p2p-circuit` и приватные/служебные IP в общий список не добавляются. До 128 уникальных пиров, до 8 адресов на пир, файл до 64 KiB. Строки `# ...` — комментарии.

Запускайте публичный узел с `--headless --reachability public`, открытым входящим WS/WSS-портом и, при использовании прямых TCP/QUIC-транспортов, их портом. Проверяйте адрес из другой сети. IPv6 публикуйте только при наличии глобального IPv6 и внешней доступности. Пример:

```sh
./p2pmessenger-linux-amd64 --headless --reachability public --port 80
```

Не отключайте работающие службы на своём сервере вслепую: выберите свободный порт или заранее настройте совместное размещение. Для привязки к 80/443 службе нужны соответствующие права. Само добавление строки не разворачивает узел и не выдаёт сертификат.

Проверка формата перед PR:

```sh
go run . --check-peers public-peers.txt
```

CI проверяет формат и публичность адресов. Доступность сервиса проверяется сопровождающим отдельно; автоматическая проверка PR не подключается к предложенным серверам. Не присылайте `identity.key`, профиль, переписку или TLS-ключи. Адрес и Peer ID из этого файла намеренно становятся публичными. Обычный PR не попадает в рабочий список до принятия сопровождающим. [Инструкция GitHub](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request-from-a-fork).

## Как клиенты используют список

- Новый запуск без `--bootstrap` использует список из `main` на GitHub. `--peer-list off` отключает его; `--peer-list URL` или `--peer-list ./my-peers.txt` задаёт другой источник.
- Ручной `--bootstrap` отключает автоматический общий список. Чтобы использовать оба источника, явно задайте URL общего списка через `--peer-list`.
- Загрузка выполняется при старте и каждые 5 минут; после ошибки — повтор через 30 секунд. Последняя корректная копия хранится в профиле и используется при недоступности источника. Некорректная загрузка не заменяет кэш; корректный пустой файл очищает список кандидатов.
- Каждые 30 секунд проверяется ограниченная выборка: текущие выбранные пиры, первые три по Peer ID и до восьми сменяющихся кандидатов. Для больших списков измерение всех узлов занимает несколько циклов. Одновременно проверяются до четырёх адресатов; попытка — до 5 секунд.
- Пробный узел с временным ключом проверяет ожидаемый Peer ID и измеряет libp2p ping. Основной узел выбирает до трёх доступных пиров с меньшим RTT в текущей выборке. Это задержка сети, не географическое расстояние и не доказательство честности сервера.
- Публичный узел резервирует одно место для доступного общего соседа с меньшим Peer ID в проверенной выборке, чтобы соединять группы с разной задержкой. Это помогает связности, но не гарантирует глобальную связность при любых отказах.
- Ручные bootstrap остаются закреплёнными. Существующие релейные пути и активные разговоры могут сохраняться помимо трёх выбранных соседей. Список — источник подключения, а не блоклист.
- AutoRelay получает обновляемый набор кандидатов без перезапуска. При возможности чат по-прежнему переходит на прямую связь.

Автоматическое подключение к общей сети зависит от наличия доступных публичных узлов в списке. Поиск сообщений остаётся ограниченным каталогом с небольшим числом переходов; список соседей не превращает его в глобальную DHT.
